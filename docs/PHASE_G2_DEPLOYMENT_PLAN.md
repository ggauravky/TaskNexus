## CI/CD, freeze and authorization

Neither workflow contains a deployment job. The Render Blueprint declares `autoDeploy: true`, so a future push/merge to its actual watched branch may deploy independently of CI. Vercel Git integration and effective branch behavior remain unknown.
- Record required status checks, branch protection/ruleset and exceptions, host deploy settings, reviewer and release permissions. Align build gates and runtime on a supported Node LTS line before rollout. Both workflows pin Node 20.19.0, which is past end of life. Verify a supported and repository-compatible line such as Node 24 on CI and both hosts. Review the audit-feed discrepancy identified in G1 before trusting a green badge. - Require a reproducible build for the exact SHA, review for both hosts, required checks before merge, and separate production approval. First establish how to hold promotion and prevent a Git trigger from deploying early. This includes deciding how to handle any future push of the security fix. Any protection or auto-deploy change requires separate approval.
- G3 authorization must name the immutable SHA, production targets and component permissions, any prerequisite migration/config scope, production smoke scope and rollback authority. Credentials, Git mutations, deployment and recovery each require explicit scope. G4 begins after G3 evidence identifies the deployed revisions.

## Recovery and rollback prerequisites

**RESTORE CAPABILITY NOT VERIFIED.** Obtain the production backup/PITR policy, latest successful backup time, snapshot or PIT selection, retention, and named recovery operator plus reviewer. Establish approved RPO and RTO. The existing 15-minute RPO and four-hour RTO are proposed objectives.

1. Under separate approval, select and double-check an isolated restore target with no application or provider integrations pointing to production. Use a recovery identity and restrict data access.
2. Record the source backup reference, recovered timestamp and recovery duration. Use temporary scoped read access to verify collection/index inventory, replica-set transactions, relationships, original and active submission versions, immutable application snapshots, and private GridFS metadata/chunks with sampled hash and access checks. Use a staging API for access checks with side effects disabled. Keep evidence sanitized.
3. Have the reviewer sign the achieved RPO/RTO and cleanup record. Revoke temporary drill access and remove the isolated target only under its approved cleanup procedure. [Backup and restore runbook](BACKUP_RESTORE.md)

Before rollout record both live and known-good deployment IDs/SHAs and configuration references, who can promote them, and whether each older artifact remains safe. For a frontend-only regression, promote the previous verified frontend if it accepts the current API. For a backend regression, hold frontend promotion, stop affected writes through the approved incident procedure when necessary, and redeploy only a safe backend revision compatible with the current frontend and persisted state. If both advanced, restore the tested pair in the rehearsed order. Recheck readiness, contract/cookies, authorization and protected file retrieval after each action. Preserve current GridFS bucket, new indexes, application snapshots, and ledger. Do not restore old JWT keys or revoked DB/SMTP credentials. Coordinate reauthentication. Account for in-flight HTTP/transactions, uploads and SSE reconnect during deployment and rollback. Use forward repair if the old code is vulnerable or cannot safely interpret committed versions or ledger records. Data compensation or restore needs separate approval. ## Controlled rollout and smoke procedure

1. Close G1 and all external blockers. Freeze the replacement SHA and obtain explicit release approval. Confirm the live revision pair and rollback records. Compare each live revision with the candidate, test old frontend/new backend in approved hosted staging, and rehearse recovery. The parent-to-candidate code review supports **backend first** because source routes and frontend application code match relative to the parent, including clients refreshing the active submission. If the actual live pairing fails the contract tests, stop and choose a coordinated cutover or compatibility fix first.
2. With front-end promotion held, apply only individually approved prerequisites. This candidate's parent diff needs no migration or index addition. Never run seeding, admin provisioning, or destructive verifiers for a routine update. Deploy the approved backend artifact to the verified Render target. Confirm revision, successful start, database readiness, logs, error/latency trend, existing API shapes and the old frontend against the new backend. Stop on failed readiness, new authorization/privacy issues, data-integrity errors, wrong SHA or breached release thresholds.
3. Promote the approved frontend artifact only after backend acceptance and if explicitly covered. Confirm revision, canonical routing and API destination, SPA refresh, HTTPS, CSP, CORS and compatibility. Run the allowed smoke checks and start the staffed observation window. Record start/end times, measured baselines, release IDs, signals, defects and any rollback actions.

## Health, observability and stabilization

`/health` answers even without MongoDB. `/api/ready` exposes only the database readiness summary and request ID and returns `503` during the local disconnect case. Startup validates config and requires MongoDB before listening. `SIGTERM`/`SIGINT` drain HTTP and SSE then close MongoDB with a bounded shutdown timer. Readiness does not probe SMTP delivery or actual GridFS fetch/stream health. Use separate alerts for those dependencies. Hosted restart/transient recovery remains unverified.

| Signal and evidence source | Initial threshold or baseline to approve | Responsible operator and response |
| --- | --- | --- |
| Frontend uptime and backend liveness/readiness, external monitor | Existing runbook proposes two consecutive 60-second failures. | Primary/backup verify host version, process and database. Pause promotion or roll back under approval. |
| 5xx, auth failures and p95 latency, request logs and host metrics | Runbook proposes 5xx over 2% for five minutes at ≥20 requests. Capture route/status baseline before choosing auth and p95 deviation thresholds. | Backend/on-call correlate by request ID, inspect transient versus user-facing failures, and halt rollout if release-caused. |
| DB connection errors, pool and capacity, Atlas and app logs | Runbook proposes connections ≥80% for five minutes, storage 80% warning/90% critical. Record normal transaction failure rate. | DB owner verifies access, pool, elections and capacity. For unexpected integrity errors pause affected writes and preserve evidence. |
| Memory and unexpected restarts, Render metrics/events | Set thresholds from pre-release RSS, limits and restart history. Page on sustained growth or restarts tied to readiness or error signals. | Service owner checks saturation, upload pressure, shutdown and deployment artifacts. |
| SSE disconnects, upload failures and task mutation failures, host/app logs and staging probes | Collect pre-release rates, distinguish normal client aborts and expected authorization denials, and approve alert thresholds. Process-local SSE metrics may need explicit instrumentation. | Backend/on-call correlates role and request ID, checks recipient-safe fallback reads, private GridFS access and transaction failures. |
| SMTP or provider errors, safe structured events and provider dashboard | Runbook proposes repeated failures over five minutes; confirm baseline and delivery policy. | Email operator reviews provider state, credentials and authorized retries without logging recipient data. |
| Backup freshness, Atlas monitoring | Page if the latest success falls outside the approved backup policy. | Recovery operator checks backup status and can stop risky changes. |

Assign primary, backup, database recovery, email, and privacy owners plus the incident channel. Test alert delivery in staging and agree acknowledgement, observation window, rollback authority, and handoff. Thresholds above are runbook proposals or decisions to make from real telemetry.
