# TaskNexus V2 — Phase F2 remediation

**Code-side gate PASS. Production security clearance BLOCKED.** The five confirmed F1 P1 findings and one later P1 regression were repaired and exercised locally. The credential-exposure release blocker requires operator evidence.

| Finding | Before | Local fix and verification |
|---|---|---|
| F-SEC-001 | Deterministic concurrent auth regression returned `200, 200` for a single refresh digest. | `authController.js` and `userData.js` condition refresh/logout on the stored digest and active status. The losing refresh returns 401 and sets no cookie. Auth tests cover old and revoked sessions. One stored session and existing cookie settings are preserved. |
| F-PRIV-001 | Anonymous Project detail returned private and opted-out member IDs. | `projectData.js`, `projectService.js`, and `projectParticipantService.js` apply active/opt-in/public filters before anonymous pagination and counts. Existing Team-member management keeps its roster. The F2 local fixture checks ID, slug, and list routes; Phase E tests still confirm showcase, candidate and snapshot boundaries. |
| F-DATA-001 | Injected internal ledger failure left the Task completed and the review partially committed. | `submissionData.reviewSubmissionAtomically` uses the current Task owner/state and active pending submission, then writes review, Task, internal ledger, audit and notification under one transaction. The controller publishes only after commit. Fixture asserts rollback on both ledger and notification failure, a zero revision allowance, one winning approval, one payment and one notification. |
| F-DATA-002 | No payment record still returned 200 and wrote a resolution audit. | `adminController.resolveDispute` accepts one decision. `paymentData.resolveDispute` refuses missing/ambiguous ledgers and transitions only unresolved records in the same transaction as the audit. Local fixture verifies missing/contradictory input, competing updates and correct release metadata. No payment provider is involved. |
| F-DATA-003 | F4's create-to-revision API fixture returned a single record after resubmission even though the revision limit counts revision records. | Reopened F2 for `submissionData.resubmitReviewedWork`. Appends a revision, preserves prior content, and changes Task/notification/audit in one transaction. Local fixture verified one winning resubmission, preserved first delivery, a denied extra revision, and one final escrow record. Existing frontend refresh reads the new active ID. |
| F-SUP-001 | Backend audit reported six affected package entries; frontend reported one. | Updated Express 4.22.3, body-parser 1.20.9, proxy-addr 2.0.8, qs 6.16.1, Mongoose 9.11.4, Nodemailer 10.6.1 and follow-redirects 1.16.3 in the lockfiles. Dependency ranges remain on existing majors. Both `npm audit --omit=dev` commands returned zero after installation. |

Local verification on 2026-11-21: F2 integration and Phase E integration passed on disposable MongoDB 8.0. Backend Jest passed 385 tests in 49 suites; standalone frontend passed 50. Backend and frontend lint, Vite build, frontend production config, backend production verifier, launch contracts, and source scan passed. The first lint run caught a stale import, which was removed. Windows file locking blocked backend `npm ci` on an ignored native bcrypt binary; `npm install` installed the locked packages and verification ran on them. Frontend `npm ci` completed. Dev dependency deprecation warnings remain outside this fix.

Compatibility notes: the review response keeps the existing shape and returns committed state. Valid approval still creates an internal escrow record with the previous commission calculation. A pre-existing ledger blocks approval for reconciliation; no records were migrated. Public roster fields are preserved for permitted entries. Refresh conflicts were tested as 200/401 and do not overwrite the winning cookie. Deployed behavior, credential rotation, and session-wide invalidation remain manual verification.

Rollback considerations: preserve already committed reviews/payments and application snapshots. Review/ledger corrections need operator reconciliation and should not be implemented as a data rollback. No production settings, schema, indexes, accounts, or credentials were changed. Retain the privacy and refresh protections when isolating unrelated regressions.
